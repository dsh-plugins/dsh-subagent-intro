# dsh-subagent-intro

子代理用哪个模型，是由当前会话里的模型自己决定的，而它对候选模型的了解全部来自提示词。工具说明只给出参数格式，`list_subagent_models` 只返回路由列表，都不包含各个模型的强项与分工。这个插件在系统提示词的子代理工具说明之前注入一段可配置的模型介绍，把每个候选模型擅长什么、什么场景下该选它直接写进上下文。配置可在 Web 设置页编辑，也可写入 profile 的 YAML。

## 功能

| 能力 | 说明 |
| --- | --- |
| 段落注入 | 在系统提示词的子代理工具说明紧前方插入一段子代理模型介绍 |
| 总述 | 由 `intro` 提供一段整体说明；留空则不输出 |
| 模型条目 | 按 `models` 的配置顺序，逐条输出展示名、模型 id、provider、能力、场景与适用时机 |
| 适用声明 | 由 `announce` 控制段首是否输出「以下子代理模型介绍仅适用于当前会话配置。历史记录中的旧版介绍以本段为准。」 |
| 路由声明 | 段末固定输出「实际可选路由以 `list_subagent_models` 工具结果为准」 |
| 工具门控 | 仅当当前作用域可见 `toolNames` 中的任一子代理创建工具时才注入；全部不可见时整段为空 |
| 头部替换 | 会话中途改写介绍内容后，直接替换头部的系统提示词，不向对话追加过期内容 |
| 空配置不注入 | `intro` 与 `models` 都未配置时整段为空，不产生任何提示词内容 |

## 安装

从 GitHub 源安装（已提交构建产物，无需授权构建脚本）：

```bash
dsh plugin --profile web add github:dsh-plugins/dsh-subagent-intro
```

也可以克隆后按本地目录安装：

```bash
git clone https://github.com/dsh-plugins/dsh-subagent-intro
dsh plugin --profile web add ./dsh-subagent-intro
```

或在 DSH Web 的「插件」管理页安装。该插件是宿主端 Bundle 插件，安装后在下一轮请求生效。修改 `lib/index.js` 后需要重启 DSH 进程；Node.js 的 ESM 模块缓存不会因为先禁用再启用就重新读取磁盘代码。构建命令见文末「开发」。

## 配置

补丁层按行 `id` 匹配并替换该行的 `config`，不与该行原有配置做深合并。不过缺失的键会由 schema 补上默认值，所以只写你要改的键就够了；下面为了完整展示字段才全部列出：

```yaml
- id: subagent-intro
  config:
    toolNames:
      - subagent
      - subagent_fork
    announce: true
    intro: |
      可委派的子代理模型各有分工，先看下面的能力与适用时机，再选择模型。
    models:
      - model: deepseek-flash
        name: 快速模型
        provider: mclans-deepseek
        ability: 快速完成单文件修改、样板代码与格式调整。
        scenario: 小步改动、批量重命名、配置调整。
        timing: 需要快速反馈且改动边界清晰时。
      - model: deep-reasoner
        name: 深思模型
        ability: 跨模块设计、疑难缺陷定位与代码审查。
        scenario: 多文件重构、算法与协议设计。
        timing: 改动波及多个模块，或需要先做取舍判断时。
```

### 字段说明

| 字段 | 类型 | 必填 | 填写建议 |
| --- | --- | --- | --- |
| `toolNames` | `string[]` | 否 | 默认 `['subagent', 'subagent_fork']`。只有列表中的工具在当前作用域可见时才注入介绍段落。除非接入了自定义的子代理创建工具，否则保持默认即可 |
| `intro` | `string` | 否 | 放在所有模型条目之前的总体原则，例如「按任务规模选模型」或「优先复用已有子代理」。具体到单个模型的信息放进 `models` |
| `announce` | `boolean` | 否 | 默认 `true`。开启后会在段首声明以当前配置为准，让模型忽略会话历史中残留的旧版介绍。仅当确定不需要覆盖历史说明时关闭 |
| `models[].model` | `string` | 是 | 模型调用子代理工具时传入的精确模型 id，应与 `list_subagent_models` 返回的 id 一致 |
| `models[].name` | `string` | 否 | 人类与模型易读的展示名，留空时回退为 `model`。填简短的中文名更便于模型在思考与回复中指代 |
| `models[].provider` | `string` | 否 | 随模型 id 一并展示的 provider id。只有同名模型挂在多个 provider 下、需要指引模型区分路由时才填 |
| `models[].ability` | `string` | 是 | 写该模型相对其他候选的差异化长处与短板（如推理深度、上下文长度、响应速度），避免只写「能力强」之类的泛化评价 |
| `models[].scenario` | `string` | 是 | 列举具体的任务形态与改动规模（如「单文件修改」「跨模块重构」「只读检索」），方便模型按手头任务直接对号入座 |
| `models[].timing` | `string` | 是 | 给出触发选择或排除该模型的边界条件（如「改动边界已明确时」「任务不要求低延迟时」）和必传参数要求 |

`models` 的条目按配置顺序输出，不排序、不去重。`model`、`ability`、`scenario`、`timing` 缺失时，插件加载阶段会因 schema 校验失败而报错，不会静默丢弃条目。

## 使用

### 在 Web 界面编辑

配置面板注册在两处，内容相同：

1. **插件详情页**：打开「插件」页，点开 `@dsh-plugin/dsh-subagent-intro`，描述下方即为配置区。这是最直接的入口。
2. **设置页**：「设置 → 插件 → 子代理介绍」分页。

面板可编辑全部字段，包括总述、模型条目（新增、删除、上下移）、工具名与适用声明头开关。输入后约 400ms 自动保存，页面顶部会显示保存状态。如果写入被宿主拒绝或失败，页面上会直接给出原因。

表单占满宿主提供的宽度，不设固定最大宽度。`model` 输入框旁的「选择」按钮会读取宿主已注册的模型目录，支持按名称或 id 过滤后点选。点选后会同时自动填入对应的 `provider`，并在 `name` 为空时补上目录里的展示名。模型目录不可用时，该按钮会禁用并提示原因，此时仍可直接手填任意模型 id。能力、场景、适用时机三个字段为多行输入，各占整行。

四个顶层配置字段都声明为 volatile，在设置页修改后**无需重启**，下一轮请求即可生效。当然，也可以继续用 YAML 补丁文件配置。

### 与 `list_subagent_models` 的关系

插件只负责注入静态介绍文本，不注册工具，不查询模型目录，也不改变实际可选路由。模型真正能用的路由以 `list_subagent_models` 工具的返回结果为准，因此段末固定输出该声明；该工具不可用时，则以子代理工具自身的描述为准。配置里写错模型 id 不会导致插件加载失败，模型在实际调用时会按工具返回的结果纠正选择。

## 行为与边界

### 注入位置

介绍段落注册在宿主系统提示词的 `subagent:model-intro`（order 2790），位于子代理工具说明 `TOOL_SUBAGENT`（order 2800）之前、`TOOL_RALPH`（order 2700）之后。宿主装配提示词时按 order 升序拼接，并自动过滤空段落，未配置内容时不会留下空行。

### 中途变更与头部替换

会话进行中如果插件热重载、修改了配置，或子代理工具的可见性发生变化，介绍段落的文本也会随之改变。此时宿主会直接替换头部的系统提示词，清除历史记录里残留的旧版介绍，而不是在对话末尾追加一条新的系统消息。

### 未配置时的行为

- `intro` 未配置或只有空白，且 `models` 为空：整段渲染为空串，不注入任何内容。
- `toolNames` 中的工具在当前作用域全部不可见（例如子代理工具未注册，或当前委派深度不允许继续创建子代理）：同样不注入。
- 段落为空时，`subagents` 相关提示词仍由宿主原有的工具说明与上下文提供，插件不产生额外影响。

### 已知限制

- 模型条目只支持单个模型 id，不支持通配符或多路由合并描述。
- `provider` 仅作为展示文本的一部分输出，不参与可见性判断；provider 维度的路由仍由工具结果决定。
- 首次遇到已有历史记录的会话时，若当前应注入的内容为空（例如子代理工具不可见），插件不会主动清除历史中的旧版介绍。这样设计是为了避免在每个新会话的首次请求上无谓地替换头部。

## 实现说明

### 头部替换机制

- 插件按 `payload.agent.session` 记录上一次贡献的完整文本。记录表是 `apply` 内的 `WeakMap`，不跨插件实例共享。
- 首次遇到某个会话时以空串为基线。这样只要当前渲染出的介绍非空，就会触发一次头部替换，把历史记录中残留的旧版介绍清掉；而新会话在还没有系统节点时，不会因此产生额外节点。
- 在 `agent/pre-step` 钩子中，插件会先用同一个渲染函数、同一份配置计算当前文本。若结果与上次相同，则原样返回 `next()` 的决定，不做任何替换。
- 若文本发生变化，则更新记录并返回 `{ ...decision, startsRequestSeries: true }`。宿主据此将该步视为新请求系列的起点，替换头部系统提示词节点并清空后续活动节点。宿主仅在当次请求的首次尝试中采纳该标记。

### 注册与生命周期

- 介绍段落通过 `ctx.systemPrompt.section({ interpolate: false })` 注册。关闭 `interpolate` 是为了防止介绍正文里的 `{{` 被当作提示词变量解析。
- 段落注册与 `agent/pre-step` 监听都包裹在 `ctx.effect(..., '<plugin>:<label>')` 内。插件卸载或热重载时会完整回收，不留监听残留。
- 段落渲染与可见性判定共用同一个 `renderFor` 闭包，保证 section 与 pre-step 两侧计算出的文本一致。
- 纯函数 `renderIntroText` 由 `test/render.test.ts` 覆盖固定文本格式。section 注册、工具可见性查询与事件监听不写单测，交由运行时直接暴露问题。
